Sample: a builder in TypeScript

This sample is a complete builder in one TypeScript file. It has the whole conversation described in Build your own builder, using only what Node.js has built in: fetch, crypto, fs and child_process. Where the code would be generated, it has a placeholder for your generator or coding agent.

The Bash and C# samples do exactly the same thing. A builder can be written in any language that speaks HTTPS and JSON, so the choice is yours.

What you need

Section titled “What you need”
  • Node.js 22.18 or later, which runs TypeScript files directly. On an older Node.js, run it with npx tsx builder.ts instead.
  • git.
  • Your organization’s name in Studio, and a maintainer of it to approve the builder. See Connect a builder and approve it.
  • A clone of the application’s repository that only the builder uses, with user.name and user.email set in Git. To push, the clone needs Git credentials of its own.

Give the builder its own clone

The builder switches branches, commits, and throws away what a failed build left behind. It refuses to start a build in a clone with uncommitted changes, but do not point it at a working copy you edit yourself.

Section titled “Run it”

  1. Clone the repository the builder should work in:

  2. Start the builder with your organization’s name, pointing it at the clone:

  3. The builder registers and shows a code. Ask a maintainer to approve it under Organization settings > Builders within 15 minutes:

  4. In the application, open Settings > Building and set Builder to this builder, or choose it for one slice. See Choose who builds.

  5. Mark a slice Ready for implementation on the board. The builder picks it up:

Press Ctrl+C to stop it. It says goodbye and shows as offline in Studio. A build that Ctrl+C interrupts is reported as failed, and Studio offers it again. Start the builder again and it reuses its credential, so it needs no new approval.

Configuration

Section titled “Configuration”

All three samples read the same environment variables.

Variable Default What it sets
STUDIO_ORGANIZATION required Your organization’s name in Studio
STUDIO_ADDRESS https://app.cratis.studio The Studio to connect to
BUILDER_NAME Sample builder (TypeScript) The name maintainers see
BUILDER_REPOSITORY the current folder The Git clone the builder works in
BUILDER_CREDENTIAL_FILE ~/.studio-builder/<organization>.json Where the builder keeps its id and token. Only your user can read it
BUILDER_COMMAND none A command to run for each build, in the clone. It gets the order’s file in STUDIO_ORDER_FILE and the part in STUDIO_PART
BUILDER_PUSH false true pushes the branch to origin after each commit. Studio-managed repository handling needs it, because Studio opens the pull request from the pushed branch

How it works

Section titled “How it works”

The file is in sections, in the order of the conversation.

Configuration. The variables above, and the manifest the builder sends when it connects. The sample builds the backend and the ui of every slice type, reads contract versions 1 to 3 and accepts either way of handling the repository. Change stacks and kit to describe your builder to people. The types after it describe only the parts of the documents the sample reads.

Talking to Studio. call sends one POST with fetch and returns the status and the parsed body. The credential goes in both Authorization and X-Studio-Builder-Credential. Every request has a timeout, and the request for work can also be cancelled by Ctrl+C. reason turns a refusal into one line.

Register once. register creates a 256-bit token, registers, saves the id and the token to BUILDER_CREDENTIAL_FILE with permissions only your user can read, and prints the approval code. connect connects, and keeps showing the code while the answer is 202. A declined or expired registration (403) makes it register again. An unknown builder (401) and any other refusal end the program with Studio’s reason.

Ask for work. work asks for work in a loop. 204 means ask again, 200 hands the slice to handle, and 409 goes back to connecting.

Handle one build. handle reads the slice, the order and the Git instructions. With Studio-managed handling it uses the branch and commit message Studio named; with builder-managed handling it chooses studio-builder/<slice id>. It starts the lease timer, switches branch, reports the step Building, runs build, commits, and reports the outcome. Anything that throws becomes a failed outcome with the reason, never a silent success.

Keep the lease. keepLease renews the lease with setInterval, every third of leaseSeconds. On 410 it records that the lease is lost; handle then throws the work away and reports nothing. progress reports a step for orders of contract version 2 or later.

Build. The placeholder. See the next section.

Repository work. prepare refuses a clone with uncommitted changes and switches to the build’s branch, creating it from the branch that was checked out when the builder started. deliver stages everything, answers nothingToDo when nothing changed, and otherwise commits, pushes when BUILDER_PUSH is true, and adds the commit, the branch and the files to the outcome. discard throws away what a build left uncommitted.

Report the outcome. report sends the outcome with the order’s contractVersion and orderId. If Studio cannot read it (400), it reports the build as failed with Studio’s reason instead.

Start. main connects and works until Ctrl+C, retries after 10 seconds when Studio cannot be reached, and disconnects at the end.

Where your generator or coding agent goes

Section titled “Where your generator or coding agent goes”

Everything between switching branch and committing happens in build. The placeholder writes a small record of each slice to studio-builds/<slice id>.json and deletes the record of each removed slice, so you can see a whole round trip in the repository. Building a slice again from the same model revision changes nothing, so the second time is reported as nothingToDo.

You can plug in your own tool in two ways:

  • Set BUILDER_COMMAND to run it without changing the code. It runs in the clone, with the build order in the file named by STUDIO_ORDER_FILE. A command that exits with anything but 0 makes the build failed. For example, BUILDER_COMMAND='./generate.sh "$STUDIO_ORDER_FILE"' runs a script of your own that calls your generator, or the command-line tool of your coding agent with the order as its task.
  • Replace the body of build to work with the order in TypeScript, for example by calling a coding agent’s SDK. Change files in the clone, leave them uncommitted, and return the outcome. For built, return the result of each specification you ran and the assumptions you made; deliver adds the commit, the branch and the files. You can also return a blocked outcome with a reason and questions.

What is in an order, and how to answer it, is in Build orders and outcomes. Its JSON schemas are published, so you can generate full types for the order and the outcome instead of the partial ones in the sample.

Next steps

Section titled “Next steps”

The sample shows the conversation, not everything a builder in production needs. Before you rely on it:

  • Build several slices at once by running several builders, each with its own clone and its own credential file, registered under its own name.
  • Back off when Studio cannot be reached, growing the wait between attempts instead of waiting a fixed 10 seconds.
  • Log what the builder does to a file or your log system, and send useful lines in progress reports, at most 100 per report and without any credential.
  • Run it as a service with systemd, launchd or a container, so it starts with the machine and restarts when it stops. Keep the credential file on storage that survives a restart, readable only by the service’s user.
  • Check the deadline in the order, and report what you have before Studio stops waiting.
