Deterministic with AI on top

A generator is good at what follows a rule: file names, type names, function signatures, wiring, one test per specification. A coding agent is good at what needs judgment: the fields of an event, the business rule in a function, the data a test needs. Deterministic with AI on top splits a build between them. The generator writes the predictable part from the order and marks every place that needs judgment. The agent fills in only those places. Your checks decide whether the result is committed.

The result is code with your structure every time, and the agent’s effort spent where it counts. For how this compares with the other ways to build, see Build a builder.

How it fits together

Section titled “How it fits together”

It is one agent build, run by cratis build with a build kit. The kit carries the generator, and:

  • permits the generator as a command, so the agent may run it;
  • tells the agent, in its prompt, to run the generator first and then fill in only the marked places. The prompt passes the generator the path of the order with the {order} placeholder;
  • verifies with the generator itself, in a check mode that fails while a file, a test or a marked place is missing, followed by the type check and the tests.

The generator never overwrites a file, so running it again on a later order adds what is new and leaves the agent’s work alone.

Note

A command the agent runs also sees the STUDIO_BUILD_ORDER and STUDIO_BUILD_OUTCOME environment variables, as a generator run with --exec does. Passing {order} in the prompt is clearer, though: the command in the agent’s log says exactly what it ran, and you can run the same command by hand.

The generator

Section titled “The generator”

The generator reads the order and, for every state change slice, writes src/<feature>/<slice>.ts and src/<feature>/<slice>.test.ts when they are not there yet. It takes the names from the specifications: event Invoice Issued becomes the type InvoiceIssued, and command Pay Invoice becomes the type PayInvoice and the function payInvoice. With --check, it changes nothing and fails while any file, test or TODO(agent) is missing. Node.js 22.18 or later runs it as it is.

The manifest

Section titled “The manifest”

What differs from the Build with AI kit:

Lines What they do
sliceTypes Only state changes: the generator writes nothing else. The CLI refuses other orders before the agent starts
verify First the generator’s check, with the order’s path filled in for {order}: every file, every test and no TODO(agent) left. Then the type check and the tests
permissions.commands The generator, so the agent can run it, with or without --check. A permitted command is a prefix, so the arguments after it are allowed
requires Node.js 22.18 or later, which runs the generator’s TypeScript directly

The generator lives in the kit, so cratis build init installs it into the project at .cratis/build/kit/generator/generate.mts, and the commands name it there. Install the kit with init rather than passing --kit <folder> to a build, or the path does not exist.

Why the split works

Section titled “Why the split works”
  • The structure never drifts. Every slice has the same files, names and test layout, however the agent phrases its code, because the agent does not decide them. Reviews get easier: a reviewer reads the marked places, not the boilerplate.
  • The agent works on less. It reads two short files with clear gaps instead of designing a slice, so it finishes sooner, uses fewer tokens and goes wrong less often.
  • The checks know the structure. The generator’s own check knows exactly what must exist, so it catches a missing test or a gap the agent skipped, which a type check and a test run cannot see: an empty test passes.
  • It grows with you. Every time you notice the agent writing the same thing on every slice, move it into the generator and mark less.

Tighten it

Section titled “Tighten it”
  • Permit fewer paths. permissions.paths can name the slice files’ folder only. The CLI commits only files inside it, whatever the agent changed.
  • Check more in verify. Add a linter or an architecture check that the agent cannot argue with. Make every command one the agent may run too, so it can see a failure before the CLI does.
  • Generate more. Wiring, registration and shared types are deterministic: generate them, and leave the agent the rules and the test data.
  • Write conventions down. Put naming and style rules in the instructions, and the ones a program can check in verify.

The inverse: AI writes, deterministic checks decide

Section titled “The inverse: AI writes, deterministic checks decide”

You can split the work the other way round: the agent writes all the code, as in Build with AI, and deterministic tools hold it to your conventions. Put them in the kit’s verify, after the type check and the tests:

Permit the same tools, so the agent runs them and fixes what they find before it reports. A command in verify that rewrites files, such as npx prettier --write src, runs before the commit, so its changes to the files the agent reported are committed with them. Add the tools to the scaffold’s package.json, with their configuration, so they are installed in every new project.
