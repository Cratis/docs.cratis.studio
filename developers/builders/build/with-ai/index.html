Build with AI

A coding agent can build a slice from its build order: read the specifications, write the code and the tests, and run them until they pass. The Cratis CLI starts the agent, keeps it to the files and commands you permit, and runs your checks itself before anything is committed. You describe your stack once, in a build kit, and the agent follows it on every slice.

This is the way to choose when you want the most code for the least effort, on any stack. Its quality depends on two things you control: the instructions the agent gets, and the checks that catch what it gets wrong. For how it compares with the other ways to build, see Build a builder.

Quick start with a registered kit

Section titled “Quick start with a registered kit”

Studio registers reference kits by name, such as node for TypeScript on the Cratis Chronicle client and cratis-csharp for .NET on Cratis Arc and Chronicle. See Registered kits.

  1. In an empty Git repository for the application, install the kit for the agent you use:

    The CLI checks that the kit’s tools are installed, scaffolds the project, copies the kit to .cratis/build/kit, and writes the kit’s instructions where the agent reads them: CLAUDE.md for Claude Code, GEMINI.md for Gemini CLI, AGENTS.md for the others.

  2. Commit what init wrote. A build starts from a clean project.

  3. Connect the machine once, and start building:

    run uses the kit and the agent that init recorded. See Run it as a builder.

To try it without Studio, save the example backend order as order.json beside the project and run cratis build once --order ../order.json --outcome ../outcome.json in the project.

Choose the agent

Section titled “Choose the agent”

Name the agent with --agent, on init (it is recorded for later builds), run, once or service install:

--agent Agent How the CLI talks to it
claude Claude Code Runs claude directly, with the kit’s permissions as its allowed tools
codex Codex Over the Agent Client Protocol, through npx -y @zed-industries/codex-acp
gemini Gemini CLI Over the Agent Client Protocol, through gemini --experimental-acp
copilot Copilot CLI Over the Agent Client Protocol, through copilot --acp
opencode OpenCode Over the Agent Client Protocol, through opencode acp
cursor, acp Cursor, or any other agent Over the Agent Client Protocol, through the command you give with --agent-command

--agent-command also replaces the command for a known agent, for example to run a particular installation. The agent must be installed and signed in on the machine: it builds with your own account and plan.

What the agent gets, and what it may do

Section titled “What the agent gets, and what it may do”

For every order, the CLI writes the order and its Screenplay documents to a folder outside the project, and starts the agent in the project with:

  • the kit’s instructions and skills, as the agent’s own instructions,
  • the Screenplay guidance and a Screenplay tool server for the order’s model, so the agent can read the model and run its specifications,
  • the kit’s prompt, with its placeholders filled from the order, followed by the rules for the outcome document: where to write it and what it may hold.

The agent works inside the kit’s permissions, and the CLI answers every request it makes:

  • It may read the project and the order’s folder.
  • It may write only the files that match permissions.paths, and its outcome file. It never writes inside .git.
  • It may run only the commands that start with an entry of permissions.commands or a verify command, followed by a space or nothing. A command that chains, pipes, redirects or substitutes another (&&, ;, |, >, `, $() is refused, whatever it starts with.
  • It never commits, pushes or switches branches. The CLI does that after verification.

An agent is never run with its permission checks switched off, and Claude Code runs without your own user settings, hooks and plugins, so a build behaves the same on every machine. An agent that stops without writing an outcome, as Copilot CLI does when a request is refused, is asked twice to go on.

Permissions are not a sandbox

A permitted command runs with your user’s rights, and a program it starts is not checked again. Permit only commands you would run yourself, such as your compiler and your test runner. The verify commands run after the agent, whatever it wrote, so a slice is never committed unless they pass.

The manifest

Section titled “The manifest”
Lines What they do
kitVersion, name, version, description Identify the kit. name is lowercase words joined by hyphens
sliceTypes The kit builds state changes and state views. The CLI refuses an order for an automation or a translation with a failed outcome, before the agent starts
scaffold Copies the scaffold folder into a new, empty project and runs npm install there
instructions, prompt The stack instructions the agent always reads, and the prompt for one order
verify Run by the CLI after the agent, in the project: the type check, then the tests of the feature. {feature} is filled from the order. Vitest fails when it finds no tests, so a slice without tests is never committed
git.commit The commit message, here Build PayInvoice
permissions.paths The agent writes only under src. It cannot change the package, the scaffold or the kit
permissions.commands The agent may run the type check and the tests, and nothing else. It may not install a package
requires init refuses to install the kit unless Node.js 22 or later and npm are on the machine

The instructions

Section titled “The instructions”

The instructions say how code is written in this stack: where a slice goes, what it is named, and how a specification becomes a test. Keep them about the stack; what to build comes from the order.

The prompt

Section titled “The prompt”

The prompt is the task for one order. The CLI fills {slices}, {part}, {feature}, {application}, {order} and {attempt}, and adds the rules for the outcome document after it.

The outcome lists the files, the result of each specification, and the decisions the agent made where the order was silent. Studio shows those assumptions on the slice, so a person can confirm them or add what was missing to the model:

The code differs from run to run: an agent is not deterministic. What does not change is what the CLI checks. When you want parts of the code to come out the same every time, generate them: see Deterministic with AI on top.

Write good instructions

Section titled “Write good instructions”
  • Point at the specifications. Every specification in the order is an acceptance criterion. Ask for one test per specification, named like it, so the outcome’s results mean something and a reviewer can find them.
  • Be concrete about the layout. Name the folder, the file and the function, with an example. An agent asked for “a slice in the feature folder” picks a folder of its own; one shown src/{feature}/<slice name>.ts writes it there.
  • Let the checks decide. Put the type check and the tests in verify, and tell the agent to run the same commands until they pass. The CLI runs them again afterwards, and only their result counts.
  • Permit little. Permit the paths the slices live in and the commands the agent needs to check its work. Leave out package installs and anything that reaches the network.
  • Ask for one command at a time. Chained and piped commands are refused, and an agent that keeps asking for them wastes its turns. Ask it to write the outcome with its file editing tool rather than a shell command.
  • Ask for assumptions. Where the order is silent, a listed assumption is better than a silent decision: it comes back to the slice in Studio.
  • Use {conventions} for existing code. A kit that builds into a project it did not scaffold learns the project’s conventions once and passes them to every build. See Existing codebases.
