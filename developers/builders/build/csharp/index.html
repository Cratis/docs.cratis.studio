Sample: a generator in C#

This sample is a generator in one C# file, run with dotnet run as a file-based app: no project file and no packages, only System.Text.Json. It is a generator: the Cratis CLI runs it for every build order, and does everything else a builder does, from connecting to Studio to committing and reporting. See Build with a generator for how the two fit together.

For every slice in the order, the generator writes a Markdown sheet with the slice’s acceptance criteria to slices/<feature>/<slice>.md in the project, and reports what it wrote. The comment in the code marks where real code generation goes.

The Bash and TypeScript samples do exactly the same thing, and write the same sheets. The language is your choice: anything the shell can start works.

What you need

Section titled “What you need”
  • The Cratis CLI, with cratis build.
  • The .NET 10 SDK or later, which runs a single .cs file with dotnet run.
  • A clean clone of the application’s repository.

The code

Section titled “The code”

Save the file as ~/slice-sheets/generate.cs, outside the application’s repository. The first run compiles it, which takes a few seconds; later runs reuse the build.

Run it once, offline

Section titled “Run it once, offline”

cratis build once runs the generator on an order from a file, without connecting to Studio, and commits what it built just as a real build does.

  1. Save the example backend order as ~/order.json.

  2. In the clone of the repository, run the generator on it:

    --verify is where your build and tests go, for example dotnet test or npm test. Every --verify command runs after the generator; one that fails turns the outcome into failed.

  3. Check the result. ~/outcome.json says built and lists slices/Invoicing/PayInvoice.md, and git log shows the commit. Run the same command again: the sheet is unchanged, so the outcome is nothingToDo and nothing is committed.

Run it for real

Section titled “Run it for real”

  1. Register the machine with your organization, once, and have a maintainer approve it with the code it shows. See Connect a builder and approve it.

  2. In the clone of the repository, start the build loop with the generator:

  3. In Studio, choose the builder for the application, and mark a slice Ready for implementation. The terminal shows the generator running, the commit, and how Studio settled the slice.

The CLI pushes each commit with your own Git credentials. Add --no-push to keep the commits local, or --once to stop after one slice.

Keep it running

Section titled “Keep it running”

On macOS and Linux, install the loop as a user service, from the clone of the repository:

It starts when you sign in and restarts when it stops. cratis build service status says where its output goes, and cratis build service uninstall removes it.

Note

To use a coding agent instead of a generator, replace --exec with --agent claude, codex, gemini, copilot or opencode. See the cratis build reference.

How it works

Section titled “How it works”

Reading the order

Section titled “Reading the order”

JsonNode.Parse reads the file STUDIO_BUILD_ORDER names, and Text reads one string from it. Build orders and outcomes lists every member, with a JSON Schema you can generate classes from. The program runs in the project folder, so the paths it writes are relative to the project.

Writing the sheet

Section titled “Writing the sheet”

The loop builds the sheet for one slice: its name and type, then each specification whose sliceId matches, as Given, When and Then. This is where your own generation goes: call a code generator, fill templates, or write the command and event files for the slice.

Nothing to do

Section titled “Nothing to do”

A sheet that is already in the project with the same content is skipped. When every sheet is unchanged, the program reports nothingToDo, so the CLI makes no empty commit.

The outcome

Section titled “The outcome”

WriteOutcome writes built with the files the program wrote, each specification as notRun (the sample runs no tests), and one assumption. The CLI adds the order’s id, the contract version and the commit. A file-based app is set up for native AOT, which turns off reflection-based JSON serialization, so the program builds the outcome from JsonNode values instead of serializing a class.

Failing

Section titled “Failing”

Any exception, such as a feature or slice name that cannot be a file name, is caught and written as a failed outcome with retryable set to false, and the program exits with 0 because it wrote an outcome. Set retryable to true for an error another attempt could get past.
