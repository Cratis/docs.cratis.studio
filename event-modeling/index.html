Event modeling in Studio

Event modeling is a way to describe how a system behaves by laying the whole story out on one timeline: what people do, what the system records, and what people see afterwards. Studio’s event model board is where a team draws that timeline together.

You do not need to know anything about software design to read one. If you can follow a storyboard, you can follow an event model.

Why teams model this way

Section titled “Why teams model this way”

Most misunderstandings in a project are not about code. They are about what the business actually does, and in which order. An event model gives product owners, domain experts, designers and developers one picture that all of them can check.

  • Everyone speaks the same words. Things on the board are named in the language of the business: Add to basket, Order placed.
  • The whole behavior is visible. Nothing hides in a hallway conversation or a developer’s head. If something happens in the system, it is on the board.
  • Gaps show early. A screen that shows data nothing ever records, or a step nobody triggers, stands out on the timeline long before anyone builds it.
  • The model can be checked. Each piece of behavior can carry examples, and Studio can run the model to see how it behaves.

The shape of a board

Section titled “The shape of a board”

A board reads left to right, as time passes. A shopper opens a page, then puts something in a basket, then checks out. Each step lands to the right of the one before.

Everything on the board is one of a few kinds of element, and each has its own color in Studio:

Element Color What it is How it is named
Command Blue Something a person or the system asks for. It can be refused. An instruction: AddToBasket
Event Orange Something that happened. A fact that is never taken back. Past tense: BasketLineAdded
Read model Green What someone looks at afterwards, built from events. A noun: BasketContents
Sticky note Yellow A question, a risk or a thought that has no home in the model yet. Plain words

Screens, automations and translations also appear on the board, and later pages explain them. The first three are the heart of it: a command goes in, an event comes out, and a read model shows the result.

Here is one step of the Acme Commerce shop, the sample project that this documentation uses throughout. A shopper adds a mug to their basket:

The shopper presses a button on a screen, which asks for AddToBasket. The shop accepts the request and records the fact BasketLineAdded. The basket page then shows BasketContents, which is built from everything that has been added.

Rows on the board belong to who does the work. A row for the Shopper holds what the shopper sees and asks for, and the system has a row of its own for the things it does without being asked. Events sit in a row of their own, so the facts of the system read as one running history.

Read it like a story

Pick any column on a board and read it top to bottom: someone asks, something happens, someone sees the result. Then move one column to the right. That is the whole technique.

How Studio’s board maps to the method

Section titled “How Studio’s board maps to the method”

Studio follows the event modeling method closely. It adds the things a team needs to keep a model alive: roles, checks and a way to carry on to working software.

In the method In Studio
The timeline The board, read left to right
A step in the story A slice: one column with one behavior
Swimlanes for people and systems Rows that belong to actors
Screens and wireframes Screens attached to slices, and the design canvas
Grouping a big model Modules and features
Examples that prove a step works Specifications written as Given, When, Then
Checking that nothing is missing Findings that point at gaps, such as a slice with no specification
Systems reacting to each other Automations and translations
